# Riset: akses agen untuk bootstrap dan deploy VPS Lajur

**Tanggal:** 2026-09-27. **Status:** riset dan usulan; belum mengubah VPS, kredensial, atau pipeline produksi.

## Ringkasan keputusan yang disarankan

Gunakan **satu sesi bootstrap yang diawasi** untuk konfigurasi awal, lalu **identitas deploy terpisah dengan operasi terbatas di sisi VPS** untuk rilis rutin. Agen menyiapkan dan menjalankan langkah secara berurutan serta memperlihatkan perubahan dan hasilnya. Pemilik hanya perlu melakukan satu tindakan awal yang tidak bisa dilewati secara teknis: memberi akses awal melalui panel/console VPS atau memasang kunci publik sementara yang sudah disepakati. Setelah bootstrap, cabut akses sementara. Pilihan ini sesuai target proyek: Ubuntu VPS, Docker yang sudah ada, reverse proxy/TLS yang sudah ada, volume persisten `/srv/lajur/*`, dan GitHub Actions untuk image serta deploy SSH. [Deployment Lajur](../operations/DEPLOYMENT.md), [arsitektur](../../ARCHITECTURE.md).

## MCP SSH untuk pemula

MCP adalah cara aplikasi agen memanggil **tool** yang disediakan sebuah server MCP. “MCP SSH” biasanya berarti server/tool MCP menyediakan operasi yang pada akhirnya memakai SSH untuk menghubungi VPS. MCP sendiri tidak menambahkan pembatasan hak sistem operasi: yang menentukan akibat nyata adalah kemampuan tool, identitas SSH yang dipakai, hak akun Linux tersebut, dan kebijakan pada VPS. Spesifikasi MCP menyatakan tool dapat dipanggil model secara otomatis, interaksi manusia tidak ditentukan protokol, dan anotasi seperti *read only* tidak boleh dipercaya tanpa mempercayai servernya. [Spesifikasi MCP Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

Alur sederhananya: `agen → tool MCP/SSH di komputer atau layanan penghubung → koneksi SSH → akun Linux di VPS → perintah`. Kunci privat SSH berada di sisi klien/penghubung yang membuat koneksi; kunci publik dipasang di `authorized_keys` milik akun VPS. Letak penyimpanan privat yang tepat bergantung pada implementasi tool yang dipilih. Jangan menaruh kunci privat, password, atau token di repo, prompt, output/log agen, maupun image Docker. Verifikasi identitas host dengan host key yang diketahui sebelum koneksi pertama; jangan menerima key baru secara buta. [Manual OpenSSH `sshd`](https://man.openbsd.org/sshd.8), [deployment Lajur](../operations/DEPLOYMENT.md).

MCP **bisa** memberi agen daftar tool seperti `inspect`, `upload`, atau `deploy`, dan UI klien bisa meminta persetujuan tiap pemanggilan. MCP **tidak otomatis bisa** menjamin perintah aman, membatasi path, mencegah pembacaan workbook, atau memaksa persetujuan jika tool/akun di belakangnya masih menerima shell bebas. DBHub MCP dalam instruksi proyek adalah jalur database; lean-ctx MCP adalah jalur baca/cari/shell konteks kerja lokal. Keduanya bukan pemberi akses VPS. Guardrail yang kuat berada pada **akun, key, forced command, izin file, dan kode operasi di sisi VPS**. [Spesifikasi MCP Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools), [OpenSSH `authorized_keys`](https://man.openbsd.org/sshd.8).

## Pilihan dan konsekuensi

| Pilihan | Kelebihan | Batas nyata |
| --- | --- | --- |
| SSH/MCP dengan akun admin sementara dan persetujuan operasi | Fleksibel untuk bootstrap awal yang belum diketahui semua detailnya; agen menangani urutan dan error | Selama sesi itu akun tetap berhak luas. Pemantauan dan prompt approval mengurangi kesalahan, tetapi bukan pembatasan hak di VPS. Cabut key segera sesudahnya. |
| Playbook bootstrap yang disimpan di repo dan dijalankan agen | Perubahan dapat ditinjau; Ansible menyediakan `--check --diff` untuk pratinjau | Check mode adalah simulasi dan beberapa task tidak melaporkan perubahan; `become` tetap melakukan eskalasi hak bila dipakai. Untuk satu VPS, playbook/script sederhana mungkin cukup. [Ansible check/diff](https://docs.ansible.com/projects/ansible-core/devel/playbook_guide/playbooks_checkmode.html), [Ansible become](https://docs.ansible.com/projects/ansible-core/devel/playbook_guide/playbooks_privilege_escalation.html). |
| MCP dengan operasi spesifik + akun deploy terikat forced command | Permukaan rilis rutin kecil dan bisa diaudit; satu operasi per tool | Butuh wrapper/script VPS yang ditinjau dan dipasang saat bootstrap; tetap harus mengaudit skrip dan seluruh hak transitive-nya. [OpenSSH `authorized_keys`](https://man.openbsd.org/sshd.8). |
| Runner GitHub Actions langsung di VPS | VPS menarik job tanpa SSH inbound tambahan | Workflow menjalankan kode di host yang menyimpan data keuangan; runner persisten dapat dikompromikan oleh kode workflow. Kurang cocok untuk VPS produksi Lajur. [GitHub Secure use](https://docs.github.com/en/actions/reference/security/secure-use). |

**Rekomendasi:** pakai opsi pertama hanya untuk bootstrap, dengan perubahan tertulis dan titik persetujuan pada tindakan berisiko; lalu gunakan opsi ketiga untuk deploy berulang. Playbook/script deklaratif dapat dipakai sebagai artefak bootstrap agar proses dapat diulang. Jangan memilih server MCP SSH pihak ketiga hanya karena mengklaim *safe*; periksa implementasi, tempat penyimpanan kunci, logging, dan apakah tool mengekspos shell arbitrer.

## Alur bootstrap pertama yang terawasi

1. Agen meninjau keadaan repo dan merancang perubahan host: user/izin, direktori `/srv/lajur/{data,backups,templates,auth,keys}`, konfigurasi Compose produksi, reverse proxy untuk domain sebenarnya, TLS, backup, dan health check. Tunjukkan diff/rencana konkret kepada pemilik sebelum operasi yang bisa mengganggu layanan lain. Deployment Lajur mengharuskan API hanya di loopback belakang reverse proxy dan data/kunci tetap di luar container. [Deployment](../operations/DEPLOYMENT.md), [Auth security](../architecture/AUTH_SECURITY.md).
2. Pemilik memberi akses awal **sementara** lewat mekanisme VPS yang sudah ia kuasai, misalnya menambahkan satu kunci publik ke akun operator melalui console provider. Agen menyimpan kunci privat hanya pada penyimpanan lokal yang dilindungi dan tidak memasukkan nilainya ke percakapan. Pastikan host key VPS dari sumber yang dipercaya sebelum menyimpan `known_hosts`. [OpenSSH `sshd`](https://man.openbsd.org/sshd.8).
3. Agen menjalankan pemeriksaan baca saja, lalu langkah bootstrap kecil yang idempoten. Simpan konfigurasi non-rahasia sebagai file untuk ditinjau. Rahasia dan template XLSM privat dipasang melalui jalur privat; gunakan salinan workbook, bukan satu-satunya asli. Tes konfigurasi Nginx/sshd sebelum reload, buat backup konfigurasi terdahulu, dan jaga sesi operator tetap terbuka sampai koneksi baru dan endpoint sehat terbukti. Prinsip backup dan validasi workbook berasal dari [Deployment](../operations/DEPLOYMENT.md) dan [Backup/Recovery](../operations/BACKUP_RECOVERY.md).
4. Sebelum menyatakan selesai, cek `docker compose config`, status container, `/health/live`, `/health/ready`, HTTPS dari luar, volume persisten, dan prosedur redeploy image lama. Catat perubahan dan hasil tanpa mengeluarkan password, token, isi workbook, atau payload finansial. [Deployment](../operations/DEPLOYMENT.md).
5. Cabut kunci bootstrap, uji bahwa ia tak lagi bekerja, dan pertahankan akses darurat pemilik secara terpisah. Ini batas waktu yang membuat fase admin sementara berakhir; MCP tidak bisa membuat hak admin sementara aman dengan sendirinya. [OpenSSH `authorized_keys`](https://man.openbsd.org/sshd.8).

**Batas kritis:** menambahkan akun `deploy` ke grup `docker` **bukan** least privilege. Docker menyatakan grup itu memberi hak setara root; daemon Docker dapat membuat container dengan bind mount filesystem host. Jika wrapper deploy pada akhirnya memberi agen kemampuan Docker CLI bebas, pembatasan forced command juga kehilangan makna. [Docker Linux post-install](https://docs.docker.com/engine/install/linux-postinstall), [Docker Engine security](https://docs.docker.com/engine/security/).

## Bentuk akses rilis rutin yang dibatasi VPS

Pasang satu kunci SSH khusus **CI deploy**, berbeda dari kunci bootstrap. Pada `authorized_keys`, gunakan pola `restrict,command="/usr/local/sbin/lajur-deploy-gate" ...`; `restrict` mematikan forwarding, PTY, dan rc, sementara `command=` mengabaikan perintah bebas dari klien. Dapat pula membatasi asal IP dengan `from=` bila alamat sumber stabil; IP runner GitHub-hosted yang berubah membuat ini perlu dievaluasi, bukan diasumsikan. `ForceCommand`/`DisableForwarding` dalam `sshd_config` adalah padanan tingkat akun. [OpenSSH `sshd`](https://man.openbsd.org/sshd.8), [OpenSSH `sshd_config`](https://man.openbsd.org/sshd_config.5).

`lajur-deploy-gate` harus **dimiliki root dan tidak bisa ditulis user deploy**. User deploy tetap di luar grup `docker`. Gate menerima hanya operasi yang ditentukan, misalnya `status` dan `deploy <digest-image-yang-valid>`; menolak semua input lain; tidak memakai `eval`, ekspansi shell input, path arbitrer, atau perintah yang disusun dari input pengguna. Bila Docker daemon masih berjalan sebagai root, berikan eskalasi **hanya** ke helper root yang dimiliki root dan mempunyai antarmuka tetap, bukan ke `docker`, shell, atau editor bebas; uji seluruh rantai izin ini. Alternatif rootless Docker mengurangi hak daemon, tetapi perlu uji kompatibilitas volume dan reverse proxy proyek. Operasi deploy mengunci agar dua rilis tidak bersamaan, menarik satu image Lajur yang spesifik, memperbarui referensi image, menjalankan Compose untuk service `api`, memeriksa health, dan mengembalikan versi lama bila gagal. Pembatasan ini adalah rancangan implementasi yang perlu diuji, bukan fitur MCP. OpenSSH memberikan forced command, sedangkan registry mendukung image digest yang mengunci versi persis. [OpenSSH `sshd`](https://man.openbsd.org/sshd.8), [Docker Engine security](https://docs.docker.com/engine/security/), [Docker rootless mode](https://docs.docker.com/engine/security/rootless/), [GHCR](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry), [Docker Compose pull](https://docs.docker.com/reference/cli/docker/compose/pull/), [Docker Compose up](https://docs.docker.com/reference/cli/docker/compose/up/).

Guardrail *lapisan klien*: expose tool bernama `status_lajur` dan `deploy_lajur_digest`, tampilkan operasi serta hasil ke pemilik, dan minta persetujuan untuk deploy produksi jika diinginkan. Guardrail *lapisan VPS*: forced command, parser input ketat, filesystem/secret permission, dan penolakan perintah di luar scope. Jika agen juga memiliki tool shell lokal yang dapat memakai kunci admin lain, atau akun deploy punya shell/Docker bebas lewat jalur lain, lapisan VPS tersebut dapat dilewati. Uji negatif (perintah sembarang, forwarding, path lain, digest tidak valid) sebelum mengandalkan batasnya. [Spesifikasi MCP Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools), [OpenSSH `sshd`](https://man.openbsd.org/sshd.8).

## Sesudah bootstrap: CI/CD

Ya, perubahan backend biasa bisa otomatis tanpa sesi agen ke VPS: merge/push ke `main` → test .NET dan workbook → build image di GitHub-hosted runner → push ke GHCR dengan `GITHUB_TOKEN` berizin `packages: write` → job deploy SSH memanggil **hanya** gate deploy dengan digest hasil build → health check → laporkan sukses/gagal. Gunakan image immutable/digest, izin `GITHUB_TOKEN` minimum, dan pin action ke full commit SHA. VPS tetap harus **mengambil image** dari registry dan memakai kredensial baca untuk image privat; `GITHUB_TOKEN` job tidak otomatis menjadi kredensial host VPS yang tahan lama. [GitHub publish Docker images](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images), [GHCR authentication](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry), [GitHub Secure use](https://docs.github.com/en/actions/reference/security/secure-use).

Repo saat ini masih memiliki Compose **lokal** dengan `build:` dan `image: lajur-api:local`; belum ada definisi image GHCR produksi atau SSH deploy. Buat Compose/override produksi eksplisit yang memakai image registry, bukan menganggap `docker compose pull` pada file lokal itu sudah cukup. [Compose lokal](../../docker-compose.yml), [Docker Compose pull](https://docs.docker.com/reference/cli/docker/compose/pull/). Phase 9 masih mencantumkan registry, SSH, reverse proxy, volume, backup sebagai pekerjaan tertunda. [Rencana MVP](../exec-plans/active/0001-mvp.md).

Jika memakai GitHub Environments untuk persetujuan produksi, periksa **paket dan visibilitas repo**: pada GitHub Free/Pro/Team, required reviewers tersedia untuk repo publik, sedangkan fitur environment bagi repo privat memiliki syarat paket tersendiri. Jika tidak tersedia, pakai kontrol lain yang memang tersedia, misalnya review PR/branch protection serta gate di VPS. GitHub-hosted runner lebih tepat untuk build daripada memasang runner persisten di VPS yang berisi workbook. [GitHub environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments), [GitHub Secure use](https://docs.github.com/en/actions/reference/security/secure-use).

Otomatisasi ini mencakup **rilis aplikasi biasa**. Perubahan reverse proxy, pembaruan host, rotasi kredensial, pemulihan backup, insiden, atau migrasi workbook masih dapat memerlukan sesi operator tersendiri. Startup image baru tidak boleh diam-diam mengubah workbook; migrasi harus eksplisit, dengan backup dan validasi. [Deployment Lajur](../operations/DEPLOYMENT.md), [Backup/Recovery](../operations/BACKUP_RECOVERY.md).
